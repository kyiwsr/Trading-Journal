# Deploying the trading journal

The browser only talks to the Vercel site. `frontend/vercel.json` forwards `/api/*` to the Render backend,
so the login cookie is first-party. The backend talks to Supabase (Postgres and screenshot storage).

You need free accounts on Supabase, Render and Vercel (signing in with GitHub is fine) and this repo on GitHub.
Steps 1 to 3 touch Supabase, 4 to 7 the hosts, 8 to 11 checks and safety nets. Do them in order.

## 1. Supabase project

1. New project, name `trading-journal`, a strong database password (keep it in a password manager), region
   Southeast Asia (Singapore). If you pick another region, change `region` in `render.yaml` to match.
2. Click Connect and copy the **Session pooler** string (host `...pooler.supabase.com`, port 5432, user
   `postgres.<project-ref>`). Put your password in place of `[YOUR-PASSWORD]`, URL-encoding any special
   characters. This is your `DATABASE_URL`.
3. Why the session pooler: the direct connection is IPv6-only unless you buy the IPv4 add-on, so IPv4 hosts and
   GitHub's runners cannot reach it. The transaction pooler (port 6543) breaks `pg_dump`. The app converts
   `postgresql://` to the psycopg driver by itself.

## 2. Screenshot bucket

1. Storage, New bucket: name `screenshots`, **not public**, file size limit 5 MB, allowed types
   `image/png, image/jpeg, image/webp`. The API enforces the same limits; the bucket is the second lock.
2. Project Settings, API: copy the Project URL (`SUPABASE_URL`) and the `service_role` key
   (`SUPABASE_SERVICE_KEY`, called the secret key in newer dashboards). Treat the key like a password. It goes
   only into Render, never into the frontend or the repo.

## 3. Migrations, your login, row-level security

From `backend/` on your own machine (PowerShell), with the pooler string from step 1:

```
$env:DATABASE_URL = "postgresql://postgres.<ref>:<password>@aws-...pooler.supabase.com:5432/postgres"
.venv\Scripts\alembic upgrade head
$env:SEED_EMAIL = "you@example.com"; $env:SEED_PASSWORD = "at least 12 characters"
.venv\Scripts\python -m scripts.seed_user
```

Do not run `seed_demo` against this database. Then, in the Supabase SQL editor, turn on row-level security so
the tables are unreachable through Supabase's own REST API (the backend's `postgres` role is unaffected):

```sql
do $$ declare t text; begin
  for t in select tablename from pg_tables where schemaname = 'public' loop
    execute format('alter table public.%I enable row level security', t);
  end loop;
end $$;
```

Run it again after any migration that adds a table.

## 4. Render backend

1. New, Blueprint, pick this repo. Render reads `render.yaml` and proposes the `trading-journal-api` web service.
2. Fill the variables it asks for:
   - `DATABASE_URL`: the session pooler string.
   - `SUPABASE_URL` and `SUPABASE_SERVICE_KEY`: from step 2.
   - `ALLOWED_ORIGIN`: `https://example.com` for now. The app refuses to start in production with a non-https
     origin, so this stands in until step 7.
3. `JWT_SECRET` is generated by Render. `TRUSTED_PROXY_HOPS` is 2 (Vercel, then Render).
4. After the first deploy, open `https://<service>.onrender.com/health`. It should answer `{"status":"ok"}`. Note
   the service URL.

## 5. Point Vercel at the backend

In `frontend/vercel.json` replace `YOUR-RENDER-SERVICE.onrender.com` with the host from step 4. Commit and push.

## 6. Vercel frontend

New Project, import the repo, set **Root Directory** to `frontend`. Vite is detected. No environment variables
are needed. Deploy, then note the production URL (`https://<project>.vercel.app`, not a per-deployment URL).

## 7. Allow the Vercel origin

On Render set `ALLOWED_ORIGIN` to that Vercel URL, with no trailing path. Render redeploys. Without this,
every login and save is refused with 403.

## 8. Smoke test

Open the Vercel URL and check each of these:

- [ ] Sign in with the step 3 email and password.
- [ ] Settings: add an account and an instrument. Log a trade with a screenshot. The image shows on the detail page.
- [ ] Dashboard and Trade Log show the trade. Export CSV downloads.
- [ ] Sign out, then reload: you land on the login page.
- [ ] Five wrong passwords, then the sixth attempt answers "Too many failed sign-in attempts". Wait 15 minutes or
      restart the Render service to clear it. It locks the real owner out too.
- [ ] Client IP check: make five wrong-password attempts with a made-up email, then sign in with the right
      credentials from another network (phone data). It should work. If it is refused, `TRUSTED_PROXY_HOPS` is
      wrong and every visitor is counted as one address.
- [ ] Cold start: leave the site idle for 20 minutes, then load it. The first request can take 30 to 60 seconds and
      the "waking up" banner shows. If Vercel's proxy gives up first and you see a 5xx or a stuck banner,
      reload once; step 9 avoids it.

## 9. Keep Render awake

Render's free service sleeps after 15 minutes idle. In UptimeRobot (free), add an HTTP monitor on
`https://<service>.onrender.com/health` every 5 minutes. One free service running all month fits inside Render's
750 free hours.

## 10. Weekly encrypted backups

1. GitHub repo, Settings, Secrets and variables, Actions, New repository secret:
   - `DATABASE_URL`: the session pooler string as `postgresql://...` (no `+psycopg`).
   - `BACKUP_PASSPHRASE`: a long random phrase. Store it in a password manager; without it the backups cannot be
     opened.
2. Actions, Database backup, Run workflow. When it finishes, download the `journal-backup` artifact. It is
   encrypted, kept 30 days, and holds the `public` schema only. Screenshots in Storage are not part of it.
3. Restore check, from `backend/` (needs `pg_restore` and a local Postgres):

```
gpg --output journal.pgdump --decrypt journal-<date>.pgdump.gpg
.venv\Scripts\python -m scripts.restore_check journal.pgdump --pg-restore "C:\Program Files\PostgreSQL\18\bin\pg_restore.exe"
```

   `--source` defaults to `DATABASE_URL`. The script restores into a scratch database on that server, compares row
   counts per table, and drops the scratch database. Trades logged after the dump show as mismatches.
4. Real restore into an empty Supabase project:
   `pg_restore --clean --if-exists --no-owner --no-privileges --dbname "<pooler url>" journal.pgdump`.

## 11. Known limits and the upgrade path

- Supabase pauses a free project after about a week without activity. Resume it from its dashboard.
- Not checked before writing this: that Render offers `PYTHON_VERSION` 3.14.7 (if the build fails, set 3.13 in
  `render.yaml`), how many `X-Forwarded-For` entries Vercel and Render add (step 8 tests it), and whether
  Supabase Storage accepts uploads from your Vercel origin without extra CORS settings (step 8 tests it).
- The login limiter lives in memory, so a restart clears it.
- If cold starts stay annoying, move the API to a paid instance (Render, or Railway at about $5 per month). Nothing
  in the code changes. Keep `TRUSTED_PROXY_HOPS` equal to the number of proxies in front, and on a paid Render
  plan move `alembic upgrade head` from `startCommand` to `preDeployCommand`.
